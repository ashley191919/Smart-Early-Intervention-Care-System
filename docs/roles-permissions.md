# Authorization 角色與權限規格草案

本文件依據 [README](../README.md) 與目前討論整理，供團隊確認。文件中的候選 Permission、權限配置、角色用途及介面設計均為「待確認」，不可直接視為實作規格或授權設定。

## 1. 已確認內容與草案狀態

### 已確認：README 記載的需求與分工

- 系統將早療個案管理與評估表單電子化，支援個案進度追蹤與資料查看。
- A Authentication 負責 Login、Logout、密碼驗證、Password Hash、JWT／Session、OTP。
- B Authorization 負責 Role、Permission、RolePermission、API Authorization、API Guard 與 403 Forbidden 權限判斷。
- C Teacher Dynamic Authorization 負責 Teacher Token、到期、撤銷、QR Code、教師指定表單存取及 Audit Log 主要架構。
- 教師動態授權需求包含家長授權教師填寫、限制指定個案與指定表單，以及填寫完成或逾期後 Token 失效。
- B 不主動實作其他模組的登入、Token、個案 CRUD、表單 CRUD 或 Dashboard。

### 已確認：本次文件整理範圍

- 使用四個主要業務角色名稱：`CASE_MANAGER`、`MEDICAL_STAFF`、`PARENT`、`TEACHER`。
- 保留 `ADMIN` 角色名稱，但不預設擁有全部權限。
- `role.read`、`permission.read`、`role_permission.update` 移出第一版清單及矩陣，僅列為未來可能延伸。
- 本次只整理文件，不修改程式碼、不建立資料庫，也不實作 Login、JWT、OTP、Teacher Token 或 QR Code。

上述角色名稱用於目前草案，不代表團隊已核准正式角色模型。所有業務授權規則仍待確認。

## 3. Permission 命名規則

以下規則均為待確認的命名提案。

| 項目 | 規則草案 | 狀態 |
|---|---|---|
| 基本格式 | `<resource>.<action>`，例如 `case.read` | 待確認 |
| 字元 | 小寫英文，多字詞使用底線 | 待確認 |
| 資源名稱 | 採單數，例如 `case`、`form` | 待確認 |
| 動作名稱 | 採具體動詞，例如 `read`、`create`、`update`、`fill`、`export` | 待確認 |

| 資料範圍 | 另外描述自己的、指派的、關聯的或全部資料；表示方式與判斷責任尚未決定 | 待確認 |
| API 對應 | 前後端採一致 Permission 字串，每個 API 對應的權限另行確認 | 待確認 |

具有 `case.read` 或 `form.read` 不代表已確定可以查看全部資料。操作權限與資料範圍需一起確認。

## 6. A Authentication 提供給 B 的資訊

已確認的分工是 A 驗證身分，B 判斷權限。以下最小介面為草案，欄位名稱、來源及責任配置均待確認。

| 資訊或介面保證 | B 的用途 | 狀態 |
|---|---|---|
| 穩定且唯一的使用者識別碼，例如 `userId` | 識別操作使用者、查詢授權資料 | 待確認 |
| 已通過 A 驗證的身分上下文 | 確保 B 使用驗證後的身分 | 待確認 |
| 角色資訊，或供 B 查詢角色的識別資訊 | 判斷角色對應權限 | 待確認：A 傳角色或 B 查詢 |
| 帳號有效狀態，或 A 已檢查有效狀態的介面保證 | 處理停用帳號 | 待確認 |

介面提案中，B 不接收密碼、Password Hash 或 OTP；JWT／Session 驗證由 A 負責，B 使用其驗證結果。

目標個案、表單及操作所需 Permission，擬由 API／業務模組提供，來源與格式待確認。B 的 403 判斷已列於 README；未登入的回應及 A／API 層的處理方式待確認。

## 7. B 與 C Teacher Token 的介面邊界

### 已確認的模組責任

| 模組 | README 記載的責任 |
|---|---|
| B | Role、Permission、RolePermission、一般 API Authorization、Guard、403 判斷 |
| C | Teacher Token、到期、撤銷、QR Code、教師指定表單存取、Audit Log 主要架構 |

### 待確認的介面提案

| 場景 | 提案 | 狀態 |
|---|---|---|
| 已登入使用者發起教師邀請 | B 檢查 `teacher.invite`；C 處理邀請及 Token。邀請者與個案關係由誰檢查需確認 | 待確認 |
| 教師使用 Token 填表 | C 驗證 Token、指定個案、指定表單及有效狀態；是否接入共用 Guard 與上下文格式需確認 | 待確認 |
| 教師同時具有一般帳號 | 一般角色權限與 Token 授權如何並存、是否可合併 | 待確認 |
| 授權事件紀錄 | C 負責 Audit Log 主要架構；B 提供的事件、欄位與失敗原因需確認 | 待確認 |

教師 Token 是否連接一般 `TEACHER` 角色或 `form.fill` Permission 尚未定案，不可直接視為一般角色或廣泛表單權限。
